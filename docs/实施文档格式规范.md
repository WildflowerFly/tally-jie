# 项目实施文档格式规范

> 文档状态：Draft v1.0  
> 提炼来源：`rs485-modbus-implementation-tasks(1).md`  
> 适用范围：项目整改、功能开发、系统重构、协议接入、数据迁移等实施类文档  
> 文档目标：统一实施文档的组织结构、任务粒度、验证方式与验收要求，使任务可执行、可测试、可追溯、可交接

## 1. 规范说明

### 1.1 核心原则

实施文档不是需求说明书的重复，也不是仅列功能名称的待办清单。文档必须说明：

1. 为什么做：对应哪些需求、问题或风险。
2. 做什么：交付哪些可观察、可验证的结果。
3. 改哪里：创建、修改、删除或重新生成哪些文件。
4. 先做什么：依赖哪些任务、决策或外部条件。
5. 怎么做：按什么步骤实施，有哪些边界和禁止事项。
6. 怎么验证：执行什么命令或操作，预期得到什么结果。
7. 怎么交付：依据什么标准验收，如何记录遗留项和验证证据。

### 1.2 约束等级

- **必须**：强制要求；不满足时，文档不能视为完整或对应任务不能验收。
- **建议**：推荐做法；不采用时应说明原因。
- **可选**：根据项目规模、技术栈与交付方式选择。

### 1.3 通用规则与项目规则的边界

- 本规范提炼原文的组织方法，不绑定原项目的业务、技术栈、协议命令或目录结构。
- 分层架构、代码生成工具、数据库类型、测试命令和权限模型必须按实际项目填写。
- 原文中的 Go、Vue、sqlc、Swagger、RS485、Modbus 等仅属于项目实例，不作为所有项目的强制要求。
- 本规范中的尖括号内容均为占位符，正式发布前必须替换或明确标记“不适用”。

## 2. 文档结构规范

### 2.1 标准章节顺序

实施文档建议沿用以下结构：

```text
# <项目/模块名称>实施任务清单

文档元信息

## 1. 执行约定
## 2. 开发前决策闸门
## 3. 依赖顺序

---

## Task 1：<任务名称>
## Task 2：<任务名称>
……
## Task N：<任务名称>

---

## 4. 需求/问题覆盖矩阵
## 5. 功能完成标准
## 6. 建议实施批次
## 7. 交付与验收记录（建议补充）
```

- 必须保留执行约定、依赖顺序、任务正文、覆盖矩阵和完成标准。
- 没有待确认决策时，保留“开发前决策闸门”章节并注明“无待确认决策”。
- 没有任务依赖时，明确写出“各任务可独立实施”，不得用空白代替说明。
- 小型项目可只有一个实施批次，但仍应明确验证和交付边界。
- 原文的核心章节顺序应保持稳定；项目专用章节可在其后补充。

### 2.2 标题层级

| 层级 | 用途 | 示例 |
| --- | --- | --- |
| `#` | 文档唯一主标题 | `# 库存管理模块实施任务清单` |
| `##` | 全局章节、独立任务 | `## 1. 执行约定`、`## Task 1：建立数据模型` |
| `###` | 章节内分组、复杂任务补充说明 | `### 1.1 架构约束` |
| 加粗复选项 | 任务内执行步骤 | `- [ ] **Step 1：先编写测试**` |

同一文档必须保持一致，不得随意混用“任务一”“Task 01”“Task 1”等编号形式。

### 2.3 文档元信息

主标题后使用引用块填写元信息：

```markdown
> 文档状态：Draft v1.0  
> 编写日期：<YYYY-MM-DD>  
> 来源：`<需求文档/审计报告路径或编号>`  
> 适用仓库：`<仓库名称或路径>`  
> 目标：<一句话描述实施目标与最终产出>
```

以上字段必须填写；可补充负责人、评审人、最后更新日期和关联版本。

建议状态：

| 状态 | 含义 |
| --- | --- |
| Draft | 草稿，范围或决策尚待确认 |
| Reviewed | 已完成评审，可按确认范围实施 |
| Implementing | 正在实施 |
| Verified | 已满足约定验收标准且具有验证证据 |
| Deprecated | 已被替代或停止适用 |

文档状态不等于任务状态。部分任务完成、测试未执行或外部联调未通过时，不得将整体标记为 `Verified`。

## 3. 全局实施约定

### 3.1 执行约定

必须在任务正文前统一说明，避免每个任务重复描述：

- **实施顺序**：原则上遵循“先测试、确认预期失败、最小实现、局部验证、全量验证”。
- **架构边界**：明确调用分层、模块职责和禁止跨越的边界。
- **数据变更**：说明版本化迁移、初始化脚本、结构定义及存量数据处理要求。
- **生成文件**：说明源文件、生成命令及禁止手工修改的产物。
- **接口与文档**：接口、协议、错误码发生变化时，必须同步相关说明和测试。
- **安全边界**：明确身份认证、资源归属、角色、租户或设备类型等隔离要求。
- **兼容策略**：说明旧接口、旧数据或旧协议的保留条件、过渡方式和退出条件。
- **未知事项**：未经确认的外部能力、参数、协议或硬件行为不得自行假设为已支持。
- **操作边界**：明确是否允许提交代码、推送、部署、删除数据及其他高风险操作；未授权不得自动执行。

纯文档、调研或环境准备任务不能合理采用测试驱动时，必须说明原因，并给出替代检查方式，不得虚构“失败测试”。

### 3.2 开发前决策闸门

涉及产品取舍、权限、安全、兼容性或外部能力的未决事项，必须先登记：

| ID | 决策 | 推荐默认值 | 阻断任务 |
| --- | --- | --- | --- |
| D-01 | <需要确认的问题> | <建议方案，或“待确认，无默认值”> | Task 2、Task 4 |
| D-02 | <外部依赖问题> | <必须由外部团队提供的依据> | Task 5 |

要求：

- 决策编号使用 `D-01`、`D-02` 等稳定编号。
- 推荐默认值只是建议，不代表已经批准。
- 决策结果应记录在任务单、决策记录或 ADR 中，并能从本文定位。
- 未确认时，只能实施不依赖该决策的部分。
- 外部依赖未满足时，相关步骤标记为 `blocked`，同时写明阻断原因和解除条件。

### 3.3 依赖顺序

先用阶段表说明整体安排，再列出关键依赖：

| 阶段 | 目标 | 任务 |
| --- | --- | --- |
| A：基础与治理 | 建立安全和数据基础 | Task 1～2 |
| B：核心业务 | 完成主要业务链路 | Task 3～4 |
| C：联调与交付 | 完成外部联调和验收 | Task 5～6 |

```text
Task 1 ─> Task 2 ─> Task 3 ─> Task 5
                   └─> Task 4 ─┘
Task 1～5 ─> Task 6 全量验收
```

- 箭头表示前置任务完成后，后置任务才能按约定范围推进。
- 必须区分硬依赖、可并行工作和持续同步工作。
- 依赖表、依赖图和任务中的 `Depends` 必须一致，且不能形成循环。
- 文档同步可随各任务持续进行；最终验收再统一检查，避免把持续同步误写成循环依赖。

## 4. 单个任务格式规范

### 4.1 任务标题与粒度

统一使用：

```markdown
## Task <连续整数>：<动作 + 实施对象 + 交付目标>
```

例如：“建立版本化数据库迁移”“实现资源归属授权”“完成状态页面与刷新机制”。

每个任务必须具有可独立描述的交付结果和验收条件。若包含多个可以独立交付、独立回退的目标，建议拆成多个任务。避免使用“优化系统”“完善功能”等无法界定完成范围的标题。

### 4.2 任务头字段

字段顺序固定为：

```markdown
**Files:**

- Create: `<新增文件路径>`
- Modify: `<修改文件路径>`
- Delete: `<删除文件路径>`
- Regenerate: `<重新生成的文件路径>`

**Covers:** <需求/问题编号>  
**Produces:** <可交付、可观察的结果>。  
**Depends:** <前置任务、决策编号、外部条件；没有则写“无”>。
```

| 字段 | 必填 | 编写要求 |
| --- | --- | --- |
| Files | 是 | 使用仓库相对路径，区分创建、修改、删除和重新生成 |
| Covers | 是 | 关联需求或问题编号；来源无编号时先建立稳定编号 |
| Produces | 是 | 描述完成后的实际能力或产物，不写“完成开发”等空泛表述 |
| Depends | 是 | 引用准确编号；外部依赖必须明确提供方与所需材料 |

可选补充：`Owner`、`Status`、`Risks`、`Rollback`、`Evidence`。若采用任务状态，建议使用 `todo / in_progress / blocked / done`，其中 `done` 必须满足本任务验收要求。

文件清单要求：

- 不涉及文件改动时写明“不涉及代码文件”，并列出调研、配置或文档产物。
- 不适用的操作类型可以省略。
- 通配符仅用于范围确实明确的同类文件，且应注明“仅实际变更文件”。
- 文件名尚需外部协议决定时，标注“暂定”，并关联对应决策。
- 不得把未知文件写成已经确定的实施事实。

### 4.3 标准执行步骤

建议采用以下顺序，按实际需要增加步骤：

1. 先编写失败测试或验收用例。
2. 运行测试，确认因目标能力缺失而出现预期失败。
3. 实现最小可用方案，明确边界与异常处理。
4. 同步相关调用方、生成文件、兼容逻辑与文档。
5. 执行局部验证与必要的全量验证。

统一使用复选框：

```markdown
- [ ] **Step 1：先编写测试**
- [ ] **Step 2：运行测试确认失败**
- [ ] **Step 3：实现最小方案**
- [ ] **Step 4：同步关联内容**
- [ ] **Step 5：验证**
```

只有实际完成且具有依据的步骤才能改为 `[x]`。`blocked`、尚未执行和不适用的步骤不得伪装为已通过；不适用项须注明原因。

### 4.4 测试与实现内容

测试覆盖应按适用情况包含：

- 正常流程与预期输出。
- 必填字段、类型、枚举、长度和数值边界。
- 未登录、权限不足、跨用户或跨租户访问。
- 重复提交、幂等、并发冲突和竞态。
- 超时、取消、重试、迟到响应和异常恢复。
- 数据迁移、旧版本兼容与回滚。
- 多实例、断线重连、进程重启和外部依赖不可用。

实现说明必须写清关键规则，而非逐行规定代码。例如：事务边界、状态迁移、锁粒度、唯一性约束、允许/禁止行为、错误码与兼容窗口。

### 4.5 命令与预期结果

- 路径、字段、接口、命令名和状态值使用行内代码。
- 多行命令使用代码块，标记 `bash`、`powershell` 或 `text`。
- 必须明确工作目录、必要环境和执行前提。
- 每组关键验证命令后使用 `Expected：` 描述可观察结果。
- 预期失败必须由目标能力缺失触发；依赖未安装、语法错误等不能代替有效失败证据。
- 测试通过、构建成功、集成通过和硬件验收通过属于不同证据，不得相互替代。
- 未运行的命令必须写“未执行”及原因，不得把计划中的 `Expected` 当作实际结果。

### 4.6 分支方案与外部阻断

互斥方案沿用 `Files（方案 A）`、`Files（方案 B）` 和 `Step 2A`、`Step 2B` 等格式。

必须先完成方案决策，只实施被选方案；未选方案标记“不采用”，不得把两条互斥路线都列为必须完成。

外部依赖示例：

```text
Status：blocked
原因：外部协议未确认。
提供方：<团队/负责人>。
解除条件：取得包含字段、时序、错误码和测试样例的确认版协议。
可先执行：不依赖该协议的数据模型和模拟接口。
```

## 5. 追溯、验收与批次规范

### 5.1 需求/问题覆盖矩阵

所有纳入本次范围的需求或问题必须出现在矩阵中：

| 需求/问题 | 解决任务 | 验收依据 |
| --- | --- | --- |
| REQ-01 <需求描述> | Task 1、Task 2 | <用例编号或完成标准条目> |
| ISSUE-01 <问题描述> | Task 3 | <回归测试或验收记录> |

- 需求到任务、任务到需求必须能双向追溯。
- 不在本次范围内的事项单独注明延期、排除或后续计划，不得漏列后默认视为已解决。
- 每个任务都必须能对应范围内的需求、问题或明确的支撑目标。

### 5.2 功能完成标准

使用可勾选条目定义整体完成标准，按项目适用性至少检查：

- 核心业务链路和异常链路均满足要求。
- 权限与资源隔离在实际服务端生效。
- 数据约束、迁移和存量兼容得到验证。
- 接口、协议、状态与错误码语义一致。
- 并发、幂等、超时及恢复策略经过测试。
- 日志、指标、限流和保留策略满足运行要求。
- 相关测试、构建、集成及外部联调通过。
- 文档、生成产物、部署与交接资料同步。
- 未完成项和阻断项如实记录。

完成标准必须可以通过测试、命令、记录或人工验收证明；避免只写“功能正常”“性能良好”“基本完成”。未满足项不得勾选，不得将整体标记为 `Verified`。

### 5.3 建议实施批次

每批按“任务范围 + 交付目标 + 验证要求”描述：

```markdown
1. Task 1～2：完成数据与安全基础；通过迁移和权限测试。
2. Task 3～4：完成核心业务闭环；通过服务端和界面验证。
3. Task 5～6：完成外部联调与最终验收；形成交付记录。
```

批次应遵循依赖顺序，控制单次变更范围。每批独立验证；涉及高风险数据或部署操作时补充回退方案。是否提交代码、发布或部署必须遵守执行约定和实际授权。

### 5.4 交付与验收记录

建议使用下表记录实际结果，而非仅保留计划：

| 任务/批次 | 验证环境与版本 | 命令/验收方法 | 实际结果 | 证据 | 遗留项 |
| --- | --- | --- | --- | --- | --- |
| <编号> | <环境、代码版本、数据库/协议版本等> | <命令或操作> | <通过/失败/未执行/阻断> | <报告、日志或记录链接> | <问题、责任人、后续安排> |

必须区分“代码已实现”“测试已通过”“外部能力已确认”和“整体已验收”。记录不得包含密钥、口令、令牌或其他敏感数据。
